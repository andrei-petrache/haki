## Findings, most severe first

### F1. High: `POST /entries/copy` grows a user's data exponentially

`backend/app/entries.py:164` (`copy_meal`, on `0f83942`). Owner: backend.

Copying breakfast onto lunch, then lunch onto breakfast, and again, adds
the two meals' sizes each time. No bound on the source, the target or the
response. Since `f420599` the same loop also copies `quick_entries`.

Run, on `1b97795`, real uvicorn and PostgreSQL, one ordinary account:
27 requests made 514,229 `meal_entries` rows (52 MB with indexes); the last
request took 13.9 s and returned 30.8 MB; uvicorn's memory went from 182 to
369 MB against the pod's 512 Mi limit. About three more requests pass that
limit, and about 33 in all fill prod's 1 Gi volume.

Not a blocker: prod's Gateway is a ClusterIP Service
(`k8s/base/gateway.yaml`), so only the 9 existing accounts can reach it. It
must not go public like this, and signup is open.

Fix: `fix/meal-entry-cap` `7e07f47` (100 entries per meal per day, food and
quick together; 409, nothing copied). Run: its 470 unit and 99 integration
tests pass, and my loop gets 409 from the point where the target would pass
100. Promote a SHA that contains it.

### F2. High, fixed before merge: the new Nginx limit key could be bypassed

`frontend/nginx.conf.template`, the `map` for `$auth_limit_key`, on
`fix/rate-limit-password-change` `e4fcfda`. Owner: frontend. `main` was
never affected.

`e4fcfda` keyed the limit on `$request_uri` (the raw URL) while the
location matches the normalized path. Run, in `haki-frontend:dev` with each
template mounted, no backend (503 = passed to the proxy, 429 = limited):

| Request | `main` | `e4fcfda` | `ac6909b` |
| --- | --- | --- | --- |
| `POST /api/auth/login` x8 | 6 pass, 2 limited | same | same |
| `POST /api//auth/login` | limited | **never limited** | limited |
| `POST /api/auth/%6cogin` | limited | **never limited** | limited |
| `PUT /api/auth//me/password` | not limited (by design) | **never limited** | limited |

`ac6909b` keys on `$uri` and `check-rate-limit.sh` now sends those URLs.
`GET` and `PUT /api/auth/me` stay unlimited on it, as intended. The
password change (`26176e8`) must not merge before this one: without it a
stolen token can guess the current password at full speed.

### F3. Medium: what a rollback to `4957cfc` does after this promotion

Ops found the first point; the rest is what else the old image does.

- Run: `FoodResponse` of `4957cfc` (`backend/app/schemas.py:80` there,
  `class FoodResponse(FoodIn)`) accepts 900 kcal and rejects 902. One food
  above 900 makes `GET /foods` a 500 for its owner. `e0d1cdc` fixes the
  response models from now on; it cannot fix the image a rollback pin runs.
  Before a pin: `SELECT count(*) FROM foods WHERE calories_per_100g > 900;`
  must be 0, as `docs/journal/promotion-readiness.md` says.
- Read: on the old image quick entries disappear from `/entries` and
  `/summary` (totals drop), favourites and catalog links are ignored, and,
  if `26176e8` is promoted, tokens refused by a password change work again
  until they expire (30 minutes). All documented in the migrations; none
  loses data.
- Read: the way back is a rollback pin on `main`, a pull request, CI, the
  promote-prod run, the approval, the bot's pull request and ArgoCD's poll
  (`k8s/README.md`, "A rollback of prod"). It was drilled on staging on
  4 November, never on prod, and the pin lives in the shared
  `k8s/components/images`, so it rolls staging back too. Expect 20 minutes
  or more. Worth one dry run on staging with this release's migrations
  before the promotion.

### F4. Medium: the metrics' `method` label is unbounded, without a token

`backend/app/metrics.py:61-62`. Owner: backend.

The route label is the template (bounded), the method is whatever the
client sent. Run: 20,000 requests with 20,000 made-up methods, no token,
created 20,000 `haki_http_requests_total` series, grew `/metrics` to
30.6 MB and uvicorn by 84 MB (4.3 KB per method). About 75,000 such
requests reach the 512 Mi limit; a restart clears it. Run: the frontend's
Nginx forwards an unknown method (`QWERTY /api/x` reached the upstream).
Not tested: whether Envoy in front does. Fix: label anything outside the
known methods as `OTHER`.

### F5. Medium: quick entries share `/entries` with a frontend that does not know them

`backend/app/entries.py:95` (`day_entries`), `frontend/src/TodayPage.tsx:346`
and `:425`, `frontend/src/api.ts:223`. Owners: frontend, backend.

Read: since `f420599`, `GET /entries` also returns quick entries, with
`food_id` and `grams` null and ids from another table. The frontend on
`main` shows them as "0 g" and deletes with `DELETE /entries/{id}`, which
deletes the user's food entry that has the same number, or answers 404.
Nothing in the UI creates a quick entry yet, so this needs someone using
the API. The frontend's fix is in `feat/foods-fast-logging`; promote the
two together, or the backend alone only knowing this.

### F6. Medium: the scripts that gate prod have no tests in CI

`scripts/check-prod-app.sh`, `check-promotion.sh`, `check-tag-pr.sh`,
`check-automerge.py`. Owner: ops.

Run (grep of `.github/workflows`): CI runs `scripts/test-guard-fetch.sh`
only. `scripts/test_check_automerge.py` (46 cases, all pass, and they catch
the four breaks I tried) is run by no job. The suites for the three shell
scripts are not in the repository (the journal mentions them in session
scratchpads). prod-guard judges a pull request with `main`'s copy, so a
pull request that weakens one of these scripts is green and the weaker rule
is first used after the merge. Put the suites in the repo and in the
`manifests` job.

### F7. Low: auto-merge (still a dry run)

Owner: ops. Both read; the second also run.

- `.github/workflows/automerge.yml:69-78` and `:139-141`: taking auto-merge
  back depends on the `act` job succeeding. If it fails (token, environment)
  the pull request stays armed after a commit that made it ineligible, and
  GitHub keeps auto-merge on for pushes by someone with write access. Fail
  the `decide` job loudly, or make the check a required one.
- `scripts/check-automerge.py:205-208`: a docs pull request becomes "not
  eligible" as soon as the tag bot's own `update-branch` adds its merge
  commit (run: `eligible docs`, then `not eligible: commit 2222222 is not by
  andrei-petrache`). So `automerge-update.yml` updates a docs pull request
  and `automerge.yml` then disarms it. Fails closed, but docs auto-merge
  cannot finish once `main` moves.

### F8. Low: the migrations take table locks with no lock timeout

`backend/migrations/versions/f187f906dc7d_...py:139-164` and the two
`ALTER TABLE users` in the queue. Owner: backend.

Run: from `3bf97e2ee106` with prod-shaped rows (9 users, 8 foods,
5 exercises), `alembic upgrade head` took 0.6 s; row counts and a checksum
of every old column of `foods` are the same after; the new columns are NULL.
Read: `ALTER TABLE` waits behind any open transaction on `foods`,
`exercises` or `users`, and every request queues behind it, up to the
Job's 300 s. A `SET lock_timeout` in `migrations/env.py` would turn that
into a failed, retried Job.

### F9. Low: gaps the tests would not notice

- Run: the catalog import accepting foods above 950 kcal passes all

  (`backend/app/catalog_import.py:115`). The comment there promises that

- Run: accepting a token whose user no longer exists passes every auth test
  (`backend/app/auth.py`, `get_current_user`). It matters when account

- Read: CI migrates an empty database only (upgrade, `alembic check`,

  besides staging's.

## Security review: what was checked

Per-user isolation, every new endpoint, read and then broken on purpose
(next section): `GET /foods?favourite=`, `GET /foods/recent`,
`PUT`/`DELETE /foods/{id}/favourite`, `POST /foods/from-catalog`,
`POST /exercises/from-catalog`, `POST /entries/copy`, `POST /entries/quick`,
`DELETE /entries/quick/{id}`, `GET /catalog/*` (shared, read-only, token
required). No way found for one user to read or change another's rows.

Password change (`26176e8`): the current password is required, older tokens
are refused through the `pwc` claim, the comparison is exact on PostgreSQL
(its test runs there). The response is now 200 with a fresh token: the
frontend must store it or the device signs itself out. A new password equal
to the current one is accepted.

Input limits: every new body and query is bounded (ids, names, grams,
calories, `q` at 100 characters and 8 words, `limit` at 100). The one
missing bound was F1. Search words hold only letters and digits, so no LIKE
wildcard reaches the query.

Rate limits: only login and signup on `main`, per client IP at Nginx;
`REAL_IP_FROM` is the same in staging and prod. Nothing else is limited,
per IP or per account.

Workflows: `guard.yml` now judges against `github.sha`, refuses when `main`
moved, and its fetch retry fails closed; `test-guard-fetch.sh` runs the
workflow's own step text. `automerge.yml` checks nothing out from the pull
request, passes user input through `env`, and asks for a read-only token in
a dry run. Residual points: F6, F7. The frontend adds no
`dangerouslySetInnerHTML`, `innerHTML` or `eval`.

Differences between prod and staging that matter here: prod has no catalog
import Job until #141 is in `main` (empty catalog, the endpoints return
empty lists); two backend replicas, each with its own metrics; no scrape.

## Test honesty: breaking the code on purpose

Each row is one deliberate break in a scratch copy, then the tests that
should notice (unit on SQLite, integration on PostgreSQL).

| Change under test | The break | Result |
| --- | --- | --- |
| Favourites | owner check removed from mark and unmark | caught, 4 unit tests |
| Recent foods | both per-user filters removed | caught, 1 |
| Copy a meal | source not filtered by user | caught, 1 |
| Copy from the catalog | "already copied" lookup not per user (foods, exercises) | caught, 1 each |
| Response models (#157) | `FoodResponse` checks `le=900` again | caught, 3 |
| Catalog API | search needs no token | caught, 1 |
| Catalog import | accepts foods above 950 kcal | **not caught** (F9) |
| Metrics | label is the raw path | caught, 2 |
| Auto-merge rules | unverified commits; rename from outside `docs/`; no file cap; any author after Dependabot's first commit | caught, 1 to 3 each, but not run by CI (F6) |
| Quick entries | delete without owner check; day not filtered by user | caught, 1 each |
| Password change (`26176e8`) | current password not checked; older tokens accepted; change not recorded | caught, 1 to 3 each, the last two on PostgreSQL too |
| Tokens | a deleted user's token accepted | **not caught** (F9) |

The isolation breaks were caught by the SQLite tests only; the PostgreSQL
suite passed with every one of them (it has no cross-user case for the new
endpoints). The queries are the same on both, so this is thin rather than
wrong.
