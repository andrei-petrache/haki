## High

### H1. Login and signup can exhaust the pod's memory (no rate limiting, 64 MiB per hash)

> **Resolved** in three commits:
> - `5c8fa21` ("Bound concurrent password hashing in the backend"): at most
>   `password_hash_concurrency` (default 4) hashes at once; after
>   `password_hash_wait_seconds` (default 2) the client gets 503 with
>   `Retry-After`.
> - `7af19a3` ("Rate limit login and signup in Nginx"): POST login/signup are
>   limited to 5/min per client IP with a burst of 5, then 429 with
>   `Retry-After: 60`; checked in CI by `frontend/scripts/check-rate-limit.sh`.
> - `5e590b1` ("Show a clear message for 429 and add Vitest"): the frontend
>   explains the 429.
>
> Behind a load balancer the Nginx limit needs the real client IP (see the
> Kubernetes / AWS notes).

- **Where:** `backend/app/security.py:9`, `backend/app/auth.py:66-90`,
  `frontend/nginx.conf:27-34`
- **What:** `PasswordHash.recommended()` uses Argon2id with
  `m=65536,t=3,p=4` (**verified**: hash prefix `$argon2id$v=19$m=65536,t=3,p=4$`),
  so every login and signup allocates 64 MiB. The endpoints are sync `def`,
  so FastAPI runs them in a thread pool of 40 threads by default: about
  2.5 GiB at full concurrency. Nothing limits requests, neither in the app
  nor in Nginx.
- **Why it matters:**
  - **Kubernetes:** a pod with a 512 MiB limit is OOM-killed after about 8
    concurrent login attempts. That is a cheap denial of service against the
    whole API.
  - **Brute force:** with no limit, the only brake on password guessing is
    the cost of Argon2.
- **Suggested fix:**
  1. **Nginx:** add rate limiting for `/api/auth/` with `limit_req_zone`
     (per client IP, for example 5 r/min with a small burst) and return 429.
  2. **App:** cap concurrent hashing, for example a
     `threading.BoundedSemaphore(4)` around `hash_password`/`verify_password`,
     so memory stays bounded whatever the traffic.
  3. **Later:** per-account lockout or backoff. Once running on AWS, AWS WAF
     rate rules in front of the load balancer.
  4. Size the pod memory limit from the cap (`4 × 64 MiB` plus the app).

### H2. Any JWT secret is accepted, including the published placeholder

> **Resolved** in `a54f1e7` ("Refuse weak or placeholder JWT secrets at
> startup"): keys under 32 bytes or starting with `change-me` stop the app
> at startup, without echoing the key; CI and test keys lengthened.

- **Where:** `backend/app/config.py:15`, `.env.example:5`,
  `backend/app/security.py:30-31`
- **What:**
  - `jwt_secret_key` is any string. PyJWT accepts a 5-character HS256 key and
    only emits an `InsecureKeyLengthWarning` (**verified**).
  - The placeholder in `.env.example`
    (`change-me-generate-with-secrets-token-urlsafe`, 45 characters) passes
    any length check, and it is public on GitHub.
- **Why it matters:** if a deployment keeps the placeholder or a short key,
  anyone can sign a token with `"sub": "<any id>"` and act as any user: full
  account takeover. Copying `.env.example` to a new environment (a Kubernetes
  Secret, an AWS SSM parameter) is exactly how this happens.
- **Suggested fix:** validate at startup with a pydantic `field_validator` on
  `jwt_secret_key`:
  - require at least 32 bytes;
  - reject the `.env.example` value and anything starting with `change-me`;
  - fail fast, so a misconfigured pod never becomes ready.

  Update CI's `JWT_SECRET_KEY` (`.github/workflows/ci.yml:100`, now 20
  characters) and the test default in `backend/tests/conftest.py:9` to
  values of 32+ characters.

## Medium

### M1. Ids above 2,147,483,647 return 500 instead of 404 (verified)

> **Resolved** in `1b8e224` ("Reject ids outside the PostgreSQL integer
> range"): `DbId`/`IdPath` in `schemas.py` answer 422 before the database;
> an API-level integration test covers the boundary on PostgreSQL.

- **Where:** `backend/app/foods.py:57`, `backend/app/foods.py:70`,
  `backend/app/entries.py:99` (path ids), `backend/app/schemas.py:69`
  (`MealEntryIn.food_id`)
- **What:** ids are unbounded Python `int`s, but the columns are PostgreSQL
  `integer`. `DELETE /foods/2147483648`, `PUT /foods/2147483648`,
  `DELETE /entries/2147483648` and `POST /entries` with that `food_id` all
  returned **500** on PostgreSQL, while `2147483647` returned 404. The
  SQLite unit tests cannot catch this.
- **Why it matters:** anyone can trigger server errors at will. That
  produces noisy alerts and stack traces in the logs, and 5xx rates are what
  Kubernetes and load balancer health signals react to.
- **Suggested fix:**
  - define `DbId = Annotated[int, Field(ge=1, le=2_147_483_647)]` in
    `schemas.py`;
  - use it for path parameters (`food_id: Annotated[int, Path(ge=1, le=...)]`)
    and for `MealEntryIn.food_id`. FastAPI then answers 422.
  - Add integration tests through the API for the boundary values.

### M2. Migrations fail when the database password contains `%`; Compose breaks on special characters (verified)

> **Resolved** in `50363a9` ("Build the database URL from separate settings"):
> the settings take `DB_USER`, `DB_PASSWORD`, `DB_HOST`, `DB_PORT` and
> `DB_NAME` (or one `DATABASE_URL`, never both) and build a SQLAlchemy `URL`
> with `URL.create`. Alembic gets that object directly, so no URL goes through
> `configparser` interpolation. Compose and CI pass the parts separately, so
> any password works unescaped.

- **Where:** `backend/migrations/env.py:13`, `compose.yaml:11`
- **What:**
  - **Alembic:** `config.set_main_option()` goes through `configparser`
    interpolation. A URL with a percent-encoded password (`p%40ss`) raises
    `ValueError: invalid interpolation syntax` (**verified**). Any password
    with `@ : / ? #` must be percent-encoded in a URL, so this hits exactly
    those passwords.
  - **Compose:** `compose.yaml` pastes the raw `POSTGRES_PASSWORD` into the
    URL, so those same characters break it there too.
- **Why it matters:** AWS RDS or Secrets Manager generated passwords commonly
  contain such characters. The `migrate` Job would fail on the first real
  deployment.
- **Suggested fix:**
  - in `env.py`, escape before setting:
    `settings.database_url.replace("%", "%%")`, or pass the URL straight to
    `create_engine`;
  - better, for Kubernetes: give the settings separate `db_host`, `db_port`,
    `db_user`, `db_password`, `db_name` fields and build the URL with
    `sqlalchemy.URL.create(...)`, which escapes correctly. Each value can then
    come from its own Kubernetes Secret key.

### M3. Access token in `localStorage` with no Content Security Policy

- **Where:** `frontend/src/App.tsx:157,166`, `frontend/nginx.conf:13-15`
- **What:** the JWT is stored in `localStorage`, and Nginx sends no
  `Content-Security-Policy`.
- **Why it matters:** any XSS, for example through a future dependency or a
  feature that renders HTML, can read the token and send it out. React's
  escaping makes XSS unlikely today, but CSP is the safety net if it happens.
- **Suggested fix:** add a CSP at server level in `nginx.conf` (test it in the
  browser; React sets inline styles through the DOM, which CSP allows):
  ```
  default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:;
  connect-src 'self'; frame-ancestors 'none'; base-uri 'self'; form-action 'self'
  ```
  Longer term, consider an `HttpOnly; Secure; SameSite=Strict` cookie instead
  of `localStorage`. It needs CSRF thinking, which `SameSite=Strict` mostly
  covers for a same-origin app.

### M4. 21 of 30 runtime Python packages are not pinned

> **Resolved** in `5fce428` ("Lock all Python dependencies with hashes"):
> `requirements.in` (direct, hand-edited) compiles into `requirements.txt`
> (all 30 packages pinned, with hashes), installed with `--require-hashes
> --no-deps`; CI checks the locks match the `.in` files. Dependabot edits the
> `.in` files and regenerates the locks (seen in `f4d867b`). Follow-up
> `960e59d` pins pip in the compile script, after a newer image's pip broke
> pip-tools 7.5.

- **Where:** `backend/requirements.txt`, `backend/Dockerfile:17`
- **What:** only the 9 direct dependencies are pinned. Starlette, pydantic,
  anyio, argon2-cffi and 17 others resolve to whatever is newest at build
  time (**verified** with a clean install).
- **Why it matters:**
  - Two builds of the same commit can contain different code, so an image
    rebuilt for a hotfix may pick up a breaking or compromised release.
  - Dependabot never proposes those updates, so they bypass review and the
    cooldown policy.
  - This contradicts the supply-chain care taken for actions (SHA pins) and
    images.
- **Suggested fix:**
  - generate a lock file with hashes, using `pip-compile --generate-hashes`
    (pip-tools) or `uv pip compile`;
  - install with `pip install --require-hashes -r requirements.lock` in the
    Dockerfile and in CI;
  - Dependabot supports `pip-compile` lock files.

  The frontend is already fine here: `package-lock.json` plus `npm ci`.

### M5. Nginx upstream `backend:8000` is hardcoded

> **Resolved** in `834e1ae` ("Make the frontend's backend address
> configurable at start"): the image ships
> `/etc/nginx/templates/default.conf.template` with `${BACKEND_URL}` (default
> `http://backend:8000`), rendered by the image's entrypoint at start;
> `NGINX_ENVSUBST_FILTER` limits the substitution to `BACKEND_URL`.

- **Where:** `frontend/nginx.conf:28`
- **What:** the backend address is fixed in the config baked into the image.
- **Why it matters:**
  - In Kubernetes the Service may be named differently
    (`haki-backend.haki.svc.cluster.local`), and changing it means
    rebuilding the image.
  - Nginx also refuses to start if the name does not resolve. That makes
    rollout ordering fragile.
- **Suggested fix:** use the official image's template support. Ship
  `/etc/nginx/templates/default.conf.template` with
  `proxy_pass ${BACKEND_URL};`, and set `BACKEND_URL` per environment: the
  image runs `envsubst` at start. In Kubernetes the Service IP is stable, so
  resolving the name once at startup is acceptable.

### M6. No logging configuration: unstructured logs and no request ids

- **Where:** `backend/app/main.py:15` (logger without configuration),
  `backend/Dockerfile:44`
- **What:**
  - The app logger relies on Python's last-resort handler, so messages carry
    no timestamp, level or format.
  - Uvicorn's access log is plain text, and nothing ties a log line to a
    request.
- **Why it matters:** in Kubernetes and CloudWatch you need JSON logs to
  filter and correlate. The 503 handler's log line, the most important one
  during an outage, is currently the least structured.
- **Suggested fix:**
  - configure logging once at startup (`logging.config.dictConfig`) with a
    JSON formatter;
  - add a small middleware that sets an `X-Request-ID` header and puts the id
    in the log records;
  - pass `--log-config` to uvicorn so its logs use the same format.

### M7. CI never runs the built images and does not scan them

> **Resolved** in two parts:
> - `bc68ce4` ("Smoke-test the full stack in CI"): the `smoke` job starts the
>   whole stack with throwaway credentials and tests it through Nginx.
> - `6107e87` ("Scan images with Trivy in CI"): both images are scanned; every
>   finding goes to the Security tab, and fixable CRITICAL/HIGH ones fail the
>   `docker` job, with expiring exceptions in `.trivyignore`. The first scan
>   found 132 such issues, all in outdated base-image packages, fixed by
>   `2c144d7` (no pip in the backend image), `3c302c2` (Alpine updates in the
>   frontend image) and the Dependabot bumps to Python 3.14.9 and nginx 1.30.6.

- **Where:** `.github/workflows/ci.yml:158-181`
- **What:** the `docker` job only builds. Nothing starts the containers, and
  nothing scans their OS packages. `pip-audit` and `npm audit` currently
  report no known vulnerabilities in shipped dependencies, and Dependabot
  alerts cover packages, but not Debian or Alpine packages inside the images.
- **Why it matters:** an image that builds but cannot start would pass CI,
  for example a file missing from the `.dockerignore` allowlist or a broken
  `CMD`. The next sprint pushes these images to a registry.
- **Suggested fix:**
  - **Smoke test:** add `load: true` to the build step, then start the image
    and hit `/health`: the backend with a dummy `DATABASE_URL`, the frontend
    with `--add-host backend:127.0.0.1` or a stub.
  - **Scan:** add a SHA-pinned Trivy step (`aquasecurity/trivy-action`) that
    fails on HIGH/CRITICAL with a fix available.

## Low

### L1. Signup reveals which emails are registered
- **Where:** `backend/app/auth.py:74-77`
- `409 Email already registered` lets anyone test whether an address has an
  account. That makes the careful timing equalization in `login` largely
  moot.
- Common trade-off for consumer apps. If enumeration matters, return the
  same response either way and send the details by email; otherwise
  document it as accepted.

### L2. Login password has no maximum length

> **Resolved** in `24858d4` ("Limit the login password length"): the same
> `PASSWORD_MAX_LENGTH` (128) as signup, plus `maxLength` in the form.
- **Where:** `backend/app/schemas.py:27`
- A 1 MB password was accepted and hashed (**verified**: 401 after hashing,
  not 422). Nginx's default 1 MB body limit helps, but in-cluster callers
  bypass Nginx.
- Fix: `Field(max_length=128)`, as on signup. It is cheap, and it reduces the
  CPU cost per request that H1 is about.

### L3. JWT settings are free-form
- **Where:** `backend/app/config.py:16-17`
- `jwt_algorithm` accepts any string (`none` happens to fail safely in
  PyJWT, **verified**), and `access_token_expire_minutes` has no bounds.
- Fix: `jwt_algorithm: Literal["HS256"] = "HS256"` and `Field(ge=1, le=1440)`
  for the expiry.

### L4. Tokens cannot be revoked; sessions end every 30 minutes
- **Where:** `backend/app/security.py:22-32`, `frontend/src/App.tsx:171-177`
- Log out only deletes the token in the browser, which stays valid up to 30
  minutes. Users are logged out mid-use every 30 minutes.
- Acceptable for now. Plan short-lived access tokens plus a refresh token
  (cookie) before real users arrive, and note that rotating
  `JWT_SECRET_KEY` logs everyone out.

### L5. Food names are unique case-sensitively
- **Where:** `backend/app/models.py:40`
- "Rice" and "rice" can coexist for the same user.
- Decide the product behavior. If they should collide, use a unique index on
  `(user_id, lower(name))` plus a migration.

### L6. Concurrent food deletion can cause a 500 when adding an entry
- **Where:** `backend/app/entries.py:93`
- `create_entry` commits without handling `IntegrityError`. If the food is
  deleted between `get_own_food` and the commit, the request fails with 500.
- Rare. Wrap the commit like `commit_or_conflict` and return 404 or 409.

### L7. Stale statement in CLAUDE.md
- **Where:** `CLAUDE.md:73`
- Says "No linter is configured yet", but ruff is configured and enforced in
  CI.

### L8. Migration template still produces old syntax
- **Where:** `backend/migrations/script.py.mako:8,16-18`
- Uses `Union[...]`. The ruff post-write hook rewrites it, but the template
  itself could use `str | Sequence[str] | None` and `collections.abc`.

### L9. CI runtime versions float, while the Dockerfiles pin them
- **Where:** `.github/workflows/ci.yml:35,111,145`, `backend/Dockerfile:7`,
  `frontend/Dockerfile:8`
- CI tests on the newest Python `3.14.x` and Node `22.x`; the images use
  3.14.4 and 22.22.1, so CI and production can differ by a patch release.
- Fix: pin exact versions in `setup-python`/`setup-node`, or add
  `.python-version` and `.nvmrc` and point the actions at them. Either way,
  remember they must move together with the Dockerfile bumps from
  Dependabot.

### L10. API docs are exposed and half-broken behind `/api`
- **Where:** `backend/app/main.py:17`
- `/api/openapi.json` publishes the full API schema. `/api/docs` loads
  `/openapi.json` (without the prefix), which Nginx answers with
  `index.html`.
- Fix: set `root_path="/api"`, and disable the docs (`docs_url=None`,
  `openapi_url=None`) outside development through a setting.

### L11. Uvicorn does not trust the proxy headers
- **Where:** `backend/Dockerfile:44`
- Behind Nginx (and later a load balancer), the backend sees Nginx's IP as
  the client, so app-level rate limiting or audit logs would be wrong.
- Fix: `--proxy-headers --forwarded-allow-ips=<proxy CIDR>`. Never use `*`
  on a publicly reachable port.

### L12. `.gitignore` only covers `.env`
- **Where:** `.gitignore:8`
- `.env.local`, `.env.production` and similar would be committable.
- Fix: add `.env.*` and `!.env.example`.

### L13. Frontend: a failed foods load can disappear silently
- **Where:** `frontend/src/TodayPage.tsx:377-406`
- Both effects share one `error` state. If loading foods fails and the day
  then loads successfully, `setError(null)` hides the foods error, and the
  "Add to this day" form never appears, with no message.
- Fix: keep a separate `foodsError`.

### L14. Frontend: a failed login right after signup leads to a confusing 409
- **Where:** `frontend/src/App.tsx:38-42`
- If signup succeeds but the following login fails (503, network), retrying
  shows "Email already registered".
- Fix: after a successful signup, switch the form to login mode before
  logging in.

### L15. Dev-only npm advisories
- **Where:** `frontend/package-lock.json`
- `npm audit` reports 12 moderate advisories, all `minimatch` through the
  ESLint toolchain. Dev-only: none of it reaches the image, and
  `npm audit --omit=dev` reports 0.
- The only "fix" offered is a breaking downgrade. Wait for the upstream
  releases; Dependabot will propose them.

### L16. The migration Job gets the JWT secret it never uses
- Found after the review, while moving to Kubernetes (S6). To be fixed
  after S6.
- **Where:** `backend/app/config.py` (`jwt_secret_key` is required),
  `backend/migrations/env.py` (imports `settings`),
  `k8s/migrate-job.yaml`
- Alembic only needs the database settings, but `Settings` refuses to load
  without `JWT_SECRET_KEY`, so the Job's pod receives the key that signs every
  token. Least privilege says a pod should get only the secrets it uses.
- Fix: split the database settings from the auth settings (for example a
  `DatabaseSettings` that `env.py` loads alone), then drop `JWT_SECRET_KEY`
  from the Job.

## Kubernetes / AWS notes (no action needed yet)

- **Database connections:** per pod, SQLAlchemy can open up to 15 (pool 5 +
  overflow 10, `backend/app/db.py:9`). Check the total against RDS
  `max_connections` as replicas grow, or add RDS Proxy or PgBouncer.
- **`readOnlyRootFilesystem`:** the backend writes nothing at runtime, so it
  is fine. `nginx-unprivileged` writes its PID and temporary files to `/tmp`:
  mount an `emptyDir` there. Since M5, the image's entrypoint also renders the
  template into `/etc/nginx/conf.d` at start: mount an `emptyDir` there too,
  or Nginx starts without the app's config.
- **Migrations:** run them as a single Job or ArgoCD `PreSync` hook. Alembic
  takes no lock, so two concurrent runs must not happen.
- **Architecture:** images are built for `linux/amd64` only. Graviton (arm64)
  nodes would need `platforms: linux/amd64,linux/arm64`.
- **HSTS:** add it where TLS terminates (load balancer or ingress), not in
  this Nginx.
- **Rate limiting behind a load balancer:** the login/signup limit keys on
  `$binary_remote_addr`. Behind a load balancer that becomes the load
  balancer's address, so the limit would apply to all users at once. Use the
  real client IP with Nginx's `realip` module: `set_real_ip_from` with the load
  balancer's addresses or CIDR, `real_ip_header X-Forwarded-For` and
  `real_ip_recursive on`. Trust `X-Forwarded-For` only from those addresses:
  otherwise any client can send its own header, spoof its IP and bypass the
  limit.
- **Rate limits per replica:** each Nginx replica keeps its own counters, so
  with N replicas a client can get up to N times the configured rate (the
  load balancer spreads its requests). Likewise the backend's hashing bound is
  per pod. For a cluster-wide limit, rate-limit at the edge (ingress
  controller or AWS WAF) or use a shared store.

## What is already good

- **IDOR protection:** every single-resource access goes through
  `get_own_food` or `get_own_entry`. `POST /entries` checks ownership of the
  referenced food too, and the tests cover cross-user update, delete and
  logging.
- **Passwords:** Argon2id via pwdlib, with a dummy-hash comparison for
  unknown emails. Password hashes are never serialized (`UserResponse`).
- **JWT validation:** algorithm pinned on decode (`algorithms=[...]`), `exp`
  and `sub` required, the user looked up on every request (deleted users lose
  access).
- **Database integrity:** constraints in the database (unique, FK
  RESTRICT/CASCADE, CHECK) and tested against real PostgreSQL. Migrations are
  checked for drift (`alembic check`) and for a full downgrade/upgrade round
  trip in CI.
- **Error handling:** 503 with `Retry-After` when the database is down, with
  details only in the server log. Liveness and readiness are correctly split.
- **Containers:**
  - multi-stage builds, pinned base images, non-root numeric users;
  - code owned by root and read-only for the app user;
  - allowlist `.dockerignore`, no secrets in the images;
  - Nginx security headers, with the `add_header` inheritance trap avoided.
- **CI:**
  - `contents: read` and `persist-credentials: false`;
  - actions pinned to SHAs;
  - PR-only cancellation, parallel jobs, caching;
  - a PostgreSQL image with a single source of truth;
  - Dependabot with cooldowns, plus a ruleset requiring all six checks.
- **Test isolation:** integration tests guarded by the `_test` database-name
  check and isolated with rolled-back transactions.

## Rezumat (în română)

Nu am găsit probleme **critice**. Bazele sunt solide: protecția IDOR e
consecventă și testată, parolele folosesc Argon2id, JWT-ul e validat corect,
constrângerile sunt în baza de date și sunt testate pe PostgreSQL real, iar
imaginile Docker și CI-ul sunt bine securizate.

Cele două probleme **mari**:

1. **Login și signup pot epuiza memoria podului.** Fiecare hash Argon2
   folosește 64 MiB și nu există nicio limită de rată. Câteva zeci de cereri
   simultane pot omorî un pod în Kubernetes.
2. **Aplicația acceptă orice cheie JWT, inclusiv cea publică din
   `.env.example`.** Cu acea cheie, oricine ar putea semna un token valid
   pentru orice utilizator.

Problemele **medii** sunt cele care ne vor încurca la mutarea în Kubernetes
și AWS:

- erori 500 la id-uri foarte mari (verificat);
- migrările crapă dacă parola bazei conține `%` (verificat);
- tokenul stă în `localStorage`, fără CSP;
- 21 de dependențe Python indirecte nu sunt fixate;
- adresa backend-ului e scrisă direct în `nginx.conf`;
- logurile nu sunt structurate;
- CI-ul construiește imaginile, dar nu le pornește și nu le scanează.

Restul sunt observații **mici**: mici bug-uri de interfață, documentație
rămasă în urmă și note de planificare.

Ordinea recomandată:

1. H2 (validarea cheii JWT), M1 și L2: puține linii de cod, câștig mare.
